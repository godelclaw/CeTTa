Programming native judgments and rules in Prime
==============================================

Status: an executable interface study and a recommended integration contract.
The helper names and sequent spelling in this directory are experimental.
The existing Prime admission and checking services establish the examples.
The full native indexed-declaration and implementation correspondence remain
under development.

Colon, formation and sequents
----------------------------

The same colon notation can serve both ordinary typing and type formation:

    (: a A)             a has type A
    (: A (u i))         A is a type in the stated universe

Formation is the latter role. A sequent supplies the context in which either
judgment is being requested. A stored colon atom is an authored declaration
or assumption; inspecting it does not supply all the formation evidence.
An ordinary definition also supplies a body, whose type can be checked.

The experimental data spelling retains that distinction:

    (quote (|- ((: A (u 0)) (: x A)) (: x A)))
    (quote (|- ((: n Nat)) (formed (At n) (u 0))))
    (quote (|- ((: n Nat)) (convert (add n Z) n Nat)))

The first is a typing request; the second includes an explicit universe;
the third requests conversion at an explicit carrier. They are data values.
The final interface may use the existing type: operation names for these
forms. The experiment does not settle a new reserved vocabulary.

Normal programming should use the current lexical context implicitly.
Metaprograms need an explicit context value for inspection, abstraction,
substitution, composition and transport. Those are two views of one judgment.
Contexts are ordered dependent telescopes; a binder may depend on its earlier
entries. Source names are display information for the underlying scoped
variables. This prototype declines repeated display names; the eventual
native interface must retain scope identities through shadowing.

There are four useful views of judgments: type formation, term typing,
type conversion and term conversion at a carrier. In a universe presentation,
formation can reuse typing at a universe while retaining that universe's
formation obligations. A request, a derivation of it, and a rule mapping
premises to a conclusion have different roles and should remain inspectable.
The current rule-code value is a candidate program. Each use checks its
claimed function type before applying it; constructing the record confers
no checking authority.

One source, several operations
------------------------------

Ordinary source can remain colon declarations and equations:

    (: plus (-> Nat Nat Nat))
    (= (plus $n Z) $n)
    (= (plus $n (S $m)) (S (plus $n $m)))

The rule-generators program produces one quoted block of those same forms.
The existing definition checker checks the block's proposed body/equations
and publishes the admitted definition. Its rules then compute in ordinary
calls and participate in native dependent checking. A bad body is refused
and does not acquire a declaration.

The prototype also generates NumberBox and BitBox datatype packages, their
constructors and projections. This changes formation and computation
together through the existing datatype declaration service. It is not a
construction of arbitrary new universe or inference rules.

Bare signatures do not say that a type is freely generated by a particular
closed constructor list. An abstract type with operations and an inductive
type can share those signatures. An inductive declaration must therefore
retain its authored family, constructor boundaries and requested eliminator;
induction and constructor discrimination cannot be inferred from colon atoms
alone. The existing .module Inductives block is an appropriate package input.

A sequent can also become an ordinary dependent function. For example,
a program takes a function f : A -> B and builds a congruence proof under
x : A, y : A, e : Id A x y. The proof uses the existing identity eliminator.
The experiment chooses display names away from the supplied syntax and has
controls for f named x and f named rule-x-0. It uses quoted subtrees during
support traversal, so a callable symbol inside a data list is not executed.

That function can be checked, applied immediately, or explicitly published
for later use. Immediate application needs no new theorem name or global
conversion policy:

    !(let* (($goal (congruence-judgment inc Nat Nat))
             ($rule (rule-code $goal)))
       (run-rule $rule (quote (Z Z (refl Z)))))

The native normalizer returns the exact source, result, source type and
normalized type. Its readout may retain application spines such as
(refl (app S Z)). A derived proof function supplies evidence; it does not
make an opaque equation automatic conversion. The opaque-unit controls keep
that boundary observable.

Where coGSLT, GSLT and OSLF fit
------------------------------

A shared presentation can have these views:

    authored declarations, judgment forms and rule schemas
                  |
           checked elaboration
             /           \
     native judgments    operational presentation
       and conversion        |
             |           evaluator and steppers
       ordinary calls        |
                         OSLF observations

GSLT LanguageDef supplies sorts, constructors, equations and directed rewrites.
The coGSLT InferenceExtension supplies additional authored judgment forms,
inference schemas and rooted conversion declarations. Its source language
has quotation and elaboration laws. Its syntax rewrites preserve the payload
being elaborated; changing an actual rule package is a separate, explicit
transformation.

CalculusLanguageDef already exposes one flat language value with that proof
layer. There need not be a nested public checker object for every layer.
RuleSchema retains an identifier, an ordered metavariable vector with binder
depths, ordered premises, a conclusion and explicit side conditions. The
existing FormationSensitiveRuleSignature separately presents the actual
fourteen formation-sensitive typing rules as proof-retaining constructors.
Its proof trees have soundness, completeness and substitution results.

The .module frontend already has parameterized theories, shared instances,
joins, constructors, inductives, equations and rewrites. Its current Block
type does not contain the whole proof-calculus extension. Connecting the
existing authoring owners to the native dependent consumer is real remaining
work; appending a new syntax block alone would not establish that connection.

An operational equation can generate directed reduction and, under the
selected typed contract, conversion closed under the relevant contexts,
symmetry and transitivity. The operational meaning of an effect or a choice
needs its own observations and need not permit replacing it inside types.
Inference-machine transitions may themselves be GSLTs; their proof states
remain distinct from the object terms whose conversion they help check.

The existing DeclarationFaces.GSLTPresentation.step_iff_congruence connects
its independently defined source program steps to the presentation's
contextual steps under the stated linearity and binding conditions. It is
not a proof that the whole C evaluator realizes every such presentation.
OSLF can study the behavior of an evaluator or proof strategy. The chosen
DTT's formation and conversion judgments still need their own specification
and justified implementation.

Primitive inference rules introduce assumptions of a chosen calculus.
Structural schema validation establishes their shape and scope. Sound
interpretation, conservative extension where claimed, and compatibility with
other computation rules require additional results. A kernel that derives
judgments relative to supplied rules does not thereby certify the consistency
of those rules. Derived rules instead expand to previously licensed inference.

Native execution and ordinary editing
------------------------------------

A mathematical definition should resolve to one identity and revision carrying
its type, checked body and executable equations. Ordinary application and
conversion must use that same resolution. The current space remains a
programmable environment; a programmer should not have to enter an isolated
proof session to call a dependent function.

Two current gaps show why that identity matters:

1. An ordinary colon declaration already occupies its name. The current
   hol:define service refuses to upgrade that declaration by checking its
   accompanying ordinary equations. The same-source-admission program keeps
   this gap visible. The quoted block authoring path avoids declaring twice,
   but does not solve the full ordinary-source admission API.
2. An ordinary equation can override an admitted definition in execution
   while native conversion still uses the admitted equations. The strict
   admitted execution view reports this conflict. The general solution must
   connect ordinary name resolution and typechecking to the same definition
   identity and revision. It should preserve explicit editing/overriding,
   with dependent evidence retaining the version it actually used.

Automatic admission on first typed use is a possible convenience, as is
explicit admission of ordinary declarations. Both need the same checked
publication and revision contract. Neither should silently introduce axioms
or change the meaning of an already retained judgment. The study recommends
settling that shared contract before choosing the default spelling.

Code values and the current prototype
------------------------------------

Quoted input stays syntax while checking. The effect control verifies that
checking a statement containing add-atom does not execute that operation.
Query inspection uses quoted request and response fields, preventing a nested
type:check from replacing the inspected statement by its Boolean result.

The current prototype explicitly evaluates a rule-producing program into a
value before checking it. That staged in-memory form works without source
printing/parsing. The final builder retains explicit lambda domain annotations so that the
result can also be synthesized and applied as a first-class function. The staged form succeeds on all three inspected builds. Direct nesting and
the additional assertion-wrapper path succeed on the current executable
(c5a57d28fef5cf30), while the older frozen normal and sanitizer executables
exhaust capacity on those paths. The probes retain this compatibility
difference separately; reproducing an old failure closes no integration gate. The parser, staging and native binding contracts must make
these programming paths agree before the interface becomes standard.

The congruence builder's name generation and source quotation are ordinary
MeTTa programs. The general hygiene and native implementation correspondence
are not proved here. The prototype refuses duplicate context display names
and currently instantiates a known explicit universe spelling; these limits
must not become universal language restrictions.

Checking the study
------------------

From the Prime draft repository:

    python3 experiments/prime_typing_judgments/check.py --cetta ./cetta

Add --probe-gaps to record the direct nesting and wrapper paths separately. The
qualification script compares complete outputs, including assertion errors,
missing results, process failures and timeouts. It hashes the executable and
sources before and after the run. The default corpus has 63 programming and
authority assertions, nine assertions reproducing open integration boundaries,
and eight declaration-boundary observations, across seven suites. A passing
boundary reproducer does not close the underlying gap.

contracts.lean exercises the shared core representation directly. The formed
context A : U1, x : A closes to a dependent function, applies to the checked
arguments U0 and the ground head, and computes by two beta occurrences to
its certified result. A changed result is refused. An undeclared type is
refused as a function domain by the formation-sensitive judgment. The driver
reuses FormationCheckedTelescopePrograms and CumulativeJoins. It does not
prove the named source adapter or C implementation correct.

Integration sequence
--------------------

- Connect the current lexical typing context and reified requests, rules and
  derivations to one shared native representation and binder implementation.
- Connect ordinary source admission, definition revision and runtime dispatch
  so that calls and conversion consume the same checked declaration.
- Connect the generated indexed-family formation, constructor, eliminator and
  computation package to those ordinary native consumers, using the existing
  .module/coGSLT owners and dependent checking evidence.
- Qualify conversion extensions contextually and under substitution; finite
  certificate checking, conversion search, normalization and interactions
  between selected rules retain their separate obligations.
- Prove the applicable source/implementation correspondences and run the joined
  native, persistence, interpretation and boundary controls.

Relevant primary precedent: Andromeda 2 exposes judgments, goals and
parametric derivations as programmable values over user-specified type
rules (https://www.andromeda-prover.org/type-theory.html). Its separation of
primitive and derived rules informs this interface. Its theory-relative
soundness does not select Prime's foundation or discharge its implementation
obligations.

Authoring forms for shared proof work
------------------------------------

The runnable clients support a ranking by programming task. A local checked
application need not acquire mutable work tickets. Shared pending work and
external replies require their resource and continuation structure explicitly.

Task                         Preferred form                 Runnable comparison
Local rule application       checked ordinary application   source-rule-programs.metta
Shared proof work            explicit read/take transform   judgment-transforms.metta
Delayed argument provider    await over that transform      interactive-judgments.metta
Conditional proposal audit   complete nested source query   query-judgments.metta
Channel receive              derived for/contract forms     interaction aliases and waiting
Resource/guard inspection    explicit source constructors   negative_queries.metta

For shared work the explicit transform ranks first: the retained source, linear
work occurrence, condition and publication are visible together. For delayed
work, await adds the lifetime that an immediate application lacks. The compact
for/contract forms rank first for a simple communication pattern and defer to
an explicit transform when several resources or conditions must be shown.
For an immediate local mathematical application, the direct checked form ranks
first; introducing a mutable workspace would add an independent protocol.
These are authoring comparisons, not measured runtime rankings.

Required structure is independent of those spellings: source-indexed checking,
ordered premise positions, distinct matching alternatives and occurrences,
explicit context/substitution, declared resource use, complete negative results,
retained request identity, and validation before publication. Operational
rewriting supplies conversion only under the selected equality contract.

Policy choices include the transform name, optional receive abbreviations,
implicit current context, scheduler order, storage representation and which
operations each facet permits. In particular the current peek facet permits
every over readable rows, while absence requires observe over its inner reads.
The dependency observation needed to validate a complete computation and the
API right named observe are separate contracts. The implementation retains the
current defaults while their typed comparison is developed.
